# Project agent memory

hubspot_flutter — an open-source HubSpot toolkit for Dart & Flutter. Read the
top-level `README.md` first: it explains the two-tier security model that
drives every design decision here.

## Layout

Independent packages under `packages/` (melos-ready via `melos.yaml`, but each
package resolves/tests on its own — melos is not required and not installed):

- `packages/hubspot_flutter` — **pure Dart** core + client-safe REST modules (Forms,
  Content Search v2, public HubDB) + backend-tier stubs. Must never depend on
  Flutter.
- `packages/hubspot_flutter_chat` — Flutter **plugin** bridging HubSpot's native
  iOS/Android chat SDKs via Pigeon.
- `packages/hubspot_flutter_forms` — Flutter UI helpers (the `HubSpotForm` widget);
  `path`-depends on `hubspot_flutter`, so it is `publish_to: none`.

## Toolchain

Requires Dart ≥ 3.12 / a recent Flutter stable on `PATH`, plus an Android SDK
with platform/build-tools 36 for the chat plugin (`compileSdk = 36`).

## Build / test

```bash
# Pure-Dart core (no Flutter needed):
cd packages/hubspot_flutter        && dart pub get && dart analyze && dart test
# Flutter packages:
cd packages/hubspot_flutter_chat   && flutter pub get && flutter analyze && flutter test
cd packages/hubspot_flutter_forms && flutter pub get && flutter analyze && flutter test
```

`dart analyze` must be clean and `dart format` applied before committing.

## Two-tier model (the core design constraint)

A mobile app cannot hold a HubSpot secret and HubSpot has no PKCE flow, so only
the client-safe modules are live; every backend-mediated module is a documented
stub that throws `HubSpotUnimplementedError`. Do not implement backend-tier
modules or embed secrets in client code. See `README.md` and
`packages/hubspot_flutter/lib/src/stubs/`.

## Chat plugin specifics

- Native channel code is generated by Pigeon from
  `packages/hubspot_flutter_chat/pigeons/messages.dart`. After editing it, regenerate:
  `dart run pigeon --input pigeons/messages.dart` (writes the committed
  `*.g.dart` / `Messages.g.kt` / `Messages.g.swift`). Never `dart format` the
  generated files — keep them byte-identical to the generator's output.
- Pigeon's generated Kotlin handlers do NOT catch synchronous throws: every
  host-API method in `HubspotChatPlugin.kt` must funnel SDK exceptions into
  its `callback(Result.failure(...))`, or the app crashes and the Dart future
  hangs.
- Android bridges `com.hubspot.mobilesdk` (artifact
  `com.hubspot.mobilechatsdk:mobile-chat-sdk-android`); the SDK reads
  `android/app/src/main/assets/hubspot-info.json` at runtime.
- iOS bridges `HubspotMobileSDK` via **SPM only** (`ios/hubspot_flutter_chat/Package.swift`).
- Android and iOS SDK versions are kept aligned (currently pinned `1.0.7`, the
  iOS SDK's latest; Android's own latest is further ahead — bump both together).
  The SDKs expose no unread-count/new-message/close observers, so the bridge
  offers only `onNewMessage` (push) and `onVisibilityChanged` (open; close is
  iOS-only). Don't re-add an unread-count stream unless the SDK gains one.
- Verify the Android native side compiles via the example app:
  `cd packages/hubspot_flutter_chat/example/android && ./gradlew :hubspot_flutter_chat:compileDebugKotlin`.
  iOS cannot be compiled on Linux (needs macOS/Xcode); verify on a device build.
